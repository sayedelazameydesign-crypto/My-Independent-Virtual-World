# معمارية MIVW المقترحة

## الهدف والنطاق

عالم مرئي يمثل مساحة عمل المستخدم، يتصل بنواة محلية تدير الذاكرة والمهام والتكاملات. يظل الوصول إلى القدرات الأساسية ممكنًا دون الواجهة المرئية؛ الواجهة ليست مصدر الحقيقة للبيانات. هذا تصميم مبدئي، وليس وصفًا لقدرات منفذة. اختيارات التقنية أدناه تعكس تصورًا سابقًا قبل الإبلاغ عن المشروع القائم؛ تُراجع بعد فحص مصدره وفق [خطة التنفيذ الحالية](existing-project-plan.md)، ولا تعني إعادة كتابته.

## المسؤوليات والحدود

| المكون | المسؤولية | خارج المسؤولية |
|---|---|---|
| العالم المرئي ولوحة القيادة | تمثيل حالة النواة وإرسال طلبات المستخدم، وإظهار التكاليف والموافقات والحالة؛ دعم العربية والإنجليزية | تخزين الحقيقة الوحيدة، أو تجاوز الحوكمة |
| العقل والمهام | اختيار محول نموذج مسموح، وتنسيق المهام والإبلاغ عن الفشل | ضمان جودة النموذج أو تفعيل مزود مدفوع تلقائيًا |
| الذاكرة | تخزين محلي دائم، تعريف البيانات، التصدير والاستعادة والتحقق | تخزين أسرار المزودين داخل النسخة المحمولة |
| العمليات والأدوات | تنفيذ عمليات محددة عبر محولات منفصلة ومحدودة الصلاحية | تشغيل أوامر أو تعديل ملفات أو إرسال بيانات دون سياسة وموافقة عند الحاجة |
| الحوكمة | فرض حدود الصلاحيات والتكلفة والموافقة وسجل العمليات الحساسة | الاعتماد على إخفاء الأزرار في الواجهة كحماية |
| الاستمرارية | فحص حالة المحولات، واختيار بديل مؤهل عند الفشل وفق السياسة | تجاوز الموافقة أو الحصة أو الخصوصية بحجة الاستمرارية |
| المحولات | ترجمة العقود إلى واجهات محلية أو خارجية وإرجاع أخطاء موحدة | جعل النواة معتمدة على واجهة مزود بعينه |

## قرارات أولية

1. **محلي أولًا:** تكون النواة والبيانات على جهاز المستخدم افتراضيًا. اختيرت SQLite للبيانات المنظمة في النسخة الأولى، ويجب إثبات التخزين والاستعادة عمليًا. لا تتطلب النواة اتصالًا خارجيًا لعرض البيانات المحلية.
2. **عالم مرئي تدريجي:** يبدأ بلوحة عمل وعناصر ثنائية الأبعاد باستخدام تقنيات الويب الأساسية، كما يوضح [مسار التنفيذ](implementation-path.md). محرك ثلاثي الأبعاد مؤجل لحين تقييم الأداء وإمكانية الوصول والترخيص والتكلفة.
3. **النموذج اختياري:** لا يلزم تنزيل نموذج أو امتلاك جهاز قوي لتشغيل الوظائف غير المعتمدة على الذكاء. توفر نموذج محلي يعتمد على موارد الجهاز وحجم التنزيل؛ عند غيابه تظهر حالة غير متاح بدل اختلاق نتيجة.
4. **السحابة اختيارية:** لا يخرج محتوى المستخدم إلى مزود خارجي إلا بعد توضيح الوجهة ونوع البيانات والحصول على الموافقة المناسبة. اختلاف الشروط بين الخدمات وخططها يتطلب مراجعة فعلية قبل التفعيل.
5. **التكلفة:** حظر المدفوع افتراضيًا، بما في ذلك التحويل إلى مزود قد يفرض تكلفة. لا يمكن للتطبيق ضمان منع رسوم مزود خارجي وحده؛ يجب ضبط حدود الإنفاق لدى المزود إن توفرت والتحقق من الاستخدام.
6. **المشروعات الأخرى:** تكامل CeliaOS وphone-google وGitHub وDrive مؤجل إلى فحص واجهاتها والتراخيص والأذونات؛ لا اعتماد حرج عليها. لا دمج لوظائف dr.mukhtar.

## مسار طلب نموذجي

1. يطلب المستخدم مهمة من الواجهة؛ تُرسل إلى النواة مع سياقها.
2. تحدد الحوكمة البيانات والأدوات والمزود المسموحين، وتطلب الموافقة عند الحاجة قبل أي أثر خارجي أو حساس.
3. يختار موجّه العقل محولًا متاحًا ومؤهلًا وفق سياسة التكلفة والخصوصية، أو يوضح عدم وجود بديل.
4. تنفذ الأداة المصرّح بها المهمة، ويُحفظ الناتج محليًا إذا اختار المستخدم أو اقتضت الوظيفة ذلك.
5. تُعرض النتيجة والحالة ومصدر التنفيذ، ويُسجل الحدث دون أسرار أو محتوى غير ضروري.

## أسئلة مؤجلة

- حدود موارد الجهاز المستهدف وتقنيات الإصدارات اللاحقة للواجهة والنواة.
- صيغة الحزمة المحمولة النهائية والتشفير الاختياري وإدارة المفاتيح.
- اختيار التراخيص بعد مراجعة التبعيات، وتحديد محولات حقيقية بعد اختبار شروطها.
