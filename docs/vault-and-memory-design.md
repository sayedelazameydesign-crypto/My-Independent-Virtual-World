# تصميم Crypto Vault وعزل ملكية الذاكرة — مقترح

## الحالة والحدود

هذه وثيقة تصميم وليست تنفيذًا أو إثباتًا لأمان الإنتاج. المستخدم اعتمد أن الذاكرة مملوكة له، وأن مشاركة الوكلاء تتطلب منحًا صريحًا؛ لا يوجد ذلك العزل في النواة الحالية. `SqliteNoteStore` والنسخ الحالية **غير مشفرة**. لا يُضاف مضيف موثوق أو واجهة أو خدمة أو خوارزمية في هذا التغيير، ولا يُدّعى وجود اتصال بـLovable.

العمل في هذه الجلسة على فرعها الحالي فقط؛ يمكن تقسيم التنفيذ إلى commits مستقلة عليه بعد مراجعة التصميم، دون تغيير `main`. لا يعني ذلك اعتماد النموذج للإنتاج أو دمجه.

## المعمارية المقترحة

```text
واجهة العالم → Trusted Host → Kernel → عقد NoteStore → EncryptedNoteStore
                    │                      │                 │
                    ├─ هوية وسياسة ومنح     └─ طلبات مؤهلة     ├─ CryptoProvider
                    ├─ موافقات وسجل محدود                     ├─ KeyManager / Vault
                    └─ مفاتيح خارج الواجهة                    └─ SQLite adapter
```

المضيف هو حد الثقة الذي يثبت هوية المستخدم وسياق الوكيل ويطبق سياسة الوصول. النواة تنسق العمل ولا تستقبل من عميل غير موثوق سياسة صلاحيات أو هوية مؤكدة. طبقة التشفير والتخزين منفصلة عن Kernel. لا يُمرر كائن التخزين الخام أو المفاتيح إلى الواجهة أو الوكيل؛ للوكلاء تُعاد فقط النتائج التي يسمح بها المضيف. إن أُدخلت عبارة المرور في واجهة الويب فستصل إليها مؤقتًا؛ لذلك يفضل إدخالها عبر قناة أصلية موثوقة عندما تتاح، ويجب تحديد قناة الإدخال ومخاطرها قبل التنفيذ، دون تخزينها أو تمريرها للوكلاء. مكتبة JavaScript داخل العملية الحالية ليست sandbox أو مصادقة.

## ملكية الذاكرة وسياسة المنح

- المستخدم الموثق هو مالك البيانات. ينتمي كل سجل إلى مساحة ومالك، ويحمل معرفًا ثابتًا ونوعًا وإصدار سجل. تُنشأ مساحات الوكلاء تحت ملكية المستخدم، وليست ملكًا مستقلاً للوكيل.
- **الرفض افتراضيًا:** لا يحصل وكيل على وصول إلى ملاحظات المستخدم أو وكيل آخر بمجرد وجوده. يمنح المستخدم صراحةً وكيلًا محددًا عمليات محددة (`read`، `create`، ولاحقًا `update`/`delete`) على مساحة أو موارد محددة. لا تعني صلاحية الكتابة حق القراءة أو العكس. تعتمد القراءة والإنشاء الموجودان فقط على التنفيذ الفعلي؛ البقية عقود مستقبلية.
- مساحة مشتركة اختيارية ينشئها المستخدم ويحدد محتوياتها والوكلاء المصرح لهم وعملياتهم؛ لا مشاركة ضمنية. إلغاء المنح يمنع الطلبات اللاحقة التي لم تبدأ، ولا يمحو ما نُسخ سابقًا أو ما رآه الوكيل من نص صريح.
- تُشتق هوية الوكيل والمالك من المضيف الموثوق، لا من حقول العميل. تمر كل عملية عبر التحقق من المنحة ونطاق المورد، لا مجرد معرفة معرّف الملاحظة. يطبق المضيف التفويض داخل عملية موثوقة، ويفحصه عند التنفيذ الفعلي؛ لا يقدم `agentId` الحالي في `Kernel.run` ضمان هوية.
- تُعرَّف ذرّية إلغاء المنح مع العمليات الجارية عند التنفيذ: في قاعدة محلية مشتركة تُفحص المنحة والأثر في معاملة أو آلية قفل واحدة؛ طلب تمت إجازته واكتملت معاملته قبل الإلغاء قد يكون قد نجح. يُختبر السباق ويظهر أثره بدل الوعد بأن الإلغاء يسحب بيانات سبق تسليمها.
- استخدام DEK واحد للمساحة لا يحقق عزلًا تشفيريًا بين الوكلاء؛ العزل هنا **تفويض في المضيف**. كود خبيث داخل نفس العملية، أو مضيف مخترق، أو وكيل حصل على النص يستطيع تجاوز هذا الافتراض. لا تُقدم هذه السياسة على أنها sandbox.

## التهديدات وما لا يحميه التشفير

يستهدف التصميم تقليل كشف محتوى السجلات والنسخ عند سرقة ملف التخزين المغلق أو تعديله، ما دامت عبارة المرور أو مفتاح الاستعادة قويين ولم يُكشفا. لا يمنع جهازًا أو مضيفًا مخترقًا أثناء فتح الخزنة، أو وكيلًا مخولًا يسيء استخدام النص الذي أُعطي له، أو إرسال المستخدم محتوى إلى مزود خارجي. لا يكفي AES-GCM لكشف حذف السجلات، أو إرجاع قاعدة البيانات كاملة إلى نسخة قديمة صحيحة؛ يتطلب كشف الرجوع مرجعًا موثوقًا خارج النسخة، وهو مؤجل ولا يُدّعى وجوده.

يظل حجم السجلات وعددها وتوقيت التعديل ومعرفات أو نطاقات مفهرسة متسربة محتملة. لا تُكتب نصوص الملاحظات أو كلمات المرور أو المفاتيح في السجلات أو أخطاء النظام أو آثار الاختبار. تجنب أنماط معرّفات قابلة للتخمين يساعد الخصوصية لكنه **ليس تفويضًا**.

## المفاتيح ودورة الخزنة

- **DEK:** مفتاح بيانات عشوائي 256-bit مستقل لكل مساحة/إصدار مفتاح. لا يُحفظ مكشوفًا؛ يبقى متاحًا للمضيف أثناء فتح الخزنة فقط، وتُقلل نسخ الذاكرة ويُقفل عند انتهاء الجلسة. محو الذاكرة بشكل مضمون غير ممكن في JavaScript والبيئات المدارة؛ لا نعد به.
- **KEK:** يشتق من عبارة مرور المستخدم باستخدام KDF قياسية من مكتبة موثوقة؛ اختيار أولي لـNode هو `scrypt` بإعدادات تُقاس على الأجهزة المستهدفة وتُحفظ في الترويسة مع salt عشوائي جديد. تُحدد حدود دنيا وعليا للمعلمات وتُتحقق قبل الحساب لمنع downgrade أو استنزاف الذاكرة؛ لا تُقبل المعلمات التي يوردها ملف غير موثوق بلا قيود. لا يضمن KDF كلمة مرور قوية ولا يمنع هجوم التخمين على نسخة مسروقة.
- يُغلف DEK بمفتاح KEK باستخدام AES-256-GCM من واجهة تشفير قياسية، مع nonce جديد ووسم تحقق، وبيانات إضافية موثقة تربط التغليف بالصيغة ومعرّف المساحة وإصدار المفتاح ومعلمات KDF. تُحفظ الترويسة والسجلات المغلفة دون كلمة المرور أو KEK أو DEK صريح.
- **تغيير عبارة المرور** يعيد تغليف DEK باستخدام salt وKEK وnonce جديدة في معاملة آمنة، دون الادعاء بأنه يلغي وصول من يملك DEK سابقًا. **تدوير DEK** عملية مختلفة: مفتاح جديد وإعادة تشفير السجلات مع اختبار التعطل، ثم إيقاف المفتاح القديم بعد التحقق؛ هي اللازمة عند الاشتباه في انكشاف DEK، ولا تسحب نسخًا قديمة أو بيانات كُشفت سابقًا.
- **الاستعادة المستقلة:** تُنشأ وسيلة استعادة اختيارية بموافقة المستخدم: مفتاح استعادة عشوائي منفصل عالي الإنتروبيا، يعرض مرة واحدة لحفظه خارج الجهاز ويستخدم لتغليف DEK منفصل عن تغليف كلمة المرور. لا يُرسل تلقائيًا أو يُحفظ في Git أو localStorage أو النسخة العادية. فقدان عبارة المرور ومفتاح الاستعادة يعني احتمال فقدان البيانات نهائيًا؛ لا باب خلفي أو استعادة مضمونة. يجب اختبار الاستعادة على جهاز آخر وتوثيق مسؤولية الحفظ قبل اعتماد الميزة.

## تشفير السجلات

- AES-256-GCM من واجهة موثوقة، بمفتاح DEK، وnonce عشوائي جديد 96-bit ووسم تحقق 128-bit لكل عملية. لا تُستخدم خوارزميات تاريخية للأمن أو شيفرة تشفير مصنوعة يدويًا. النماذج الأولية لا تخلط مفاتيح السجلات والتغليف والنسخ في غرض واحد.
- تُربط بالـAAD، بترميز محدد وحتمي ومُراجع قبل التنفيذ، نسخة التنسيق والخوارزمية و`keyId` ومالك السجل ومساحته ونوعه ومعرفه وإصدار محتواه. تبديل سجل أو حقوله المرتبطة إلى سجل آخر يجب أن يفشل التحقق. AAD واضح لكنه موثّق وليس مشفرًا.
- لكل DEK ميزانية استخدام محافظة تُضبط قبل الإنتاج، وتُحسب كل محاولة تشفير حتى لو فشلت عملية الحفظ. العشوائية وحدها لا تمنع تصادم nonce نظريًا؛ يجب حد الاستخدام ومراقبته والتدوير قبل بلوغه. إذا استُعيدت لقطة قديمة بما قد يُرجع عداد الاستخدام، يُنشأ DEK جديد قبل السماح بكتابات جديدة؛ لا تدّعي قاعدة بيانات محلية وحدها اكتشاف الرجوع الخبيث. تُدرس سيناريوهات النسخ المتزامنة والأجهزة المتعددة قبل التنفيذ.
- ترويسة كل سجل تحمل نسخة وخوارزمية و`keyId` وnonce وciphertext وtag، إضافة إلى بيانات النطاق اللازمة للـAAD. جميع الأطوال والصيغ والمعرّفات تُفحص قبل تخصيص موارد كبيرة أو فك التشفير. خطأ التحقق يُعرض دون بيانات سرية، ولا يُعاد نص قبل نجاح التوثيق.
- المقصود **تشفير محتوى السجلات داخل SQLite**، وليس تشفير صفحات قاعدة البيانات أو كل البيانات الوصفية وملفات WAL تلقائيًا. إن اختير لاحقًا تشفير قاعدة كاملة، فيحتاج مراجعة اعتماداته وترخيصه واختباراته منفصلًا.

## النسخ والاستعادة

تصميم مستقبلي منفصل عن تصدير JSON الحالي: يستخدم كل تصدير DEK عشوائيًا مستقلًا للنسخة، ويُغلف بمفتاح مشتق من عبارة مرور النسخة أو بمفتاح استعادة مستقل، مع salt وnonce جديدين. يُوضح المستخدم أن النتيجة مشفرة فقط عندما يكون هذا المسار قد نُفذ واختُبر؛ لا تتحول واجهة التصدير الحالية إليه تلقائيًا.

لمعالجة البيانات الكبيرة دون حد 10,000 الحالي، يُصمم تنسيق متدرج بإصدار وحدود موارد صريحة، ومقاطع موثقة كلٌ بنونص فريد، مع بيان نهائي موثق يربط ترتيب المقاطع وعددها وتجزئاتها لكشف الحذف والاقتطاع وإعادة الترتيب. تُثبت تفاصيل الصيغة والأحجام وترميز AAD باختبارات توافق ومراجعة أمنية قبل التنفيذ؛ لا يُخترع بروتوكول جديد دون مراجعة. تُتحقق الاستعادة من كامل النسخة قبل نشرها، وتُستعاد إلى مخزن جديد بمعاملة أو آلية استبدال آمنة؛ لا تُكتب البيانات غير المشفرة في ملفات مؤقتة مكشوفة. عند الاستعادة تُنشأ مفاتيح بيانات جديدة للكتابات المستقبلية. فشل التحقق لا يغير البيانات الحالية.

النسخة المشفرة لا تحتوي كلمة المرور أو المفتاح صريحًا، لكنها تحتاج كلمة مرور النسخة أو مفتاح الاستعادة ونسخة من ترويسة التغليف. لا يشمل ذلك تلقائيًا السجلات أو الأسرار أو التبعيات الخارجية. استعادة بيانات على جهاز آخر تعتمد على امتلاك معلومات الاستعادة الصحيحة، لا على إرسال المفاتيح مكشوفة إلى خدمة.

## الترحيل من البيانات الحالية

التصميم لا يحوّل SQLite الحالية أو JSON القديمة تلقائيًا. قبل النقل يُعرض للمستخدم أن المصدر والنسخة الاحتياطية الحالية plaintext، وتُطلب موافقته. تُنشأ خزنة جديدة ثم تُنسخ السجلات وتُتحقق أعدادها ومحتوياتها وصلاحياتها؛ يُحافظ على الأصل حتى اعتماد المستخدم نجاح الاستعادة. حذف الأصل أو ادعاء محو آمن من الأقراص والنسخ والـWAL غير مضمون ويحتاج خطوة مستقلة واضحة. لا تُتلف البيانات أو تُحوّل دون موافقة.

## خطة التسليم ومعايير القبول

1. **K1:** توثيق الاختبار المحلي لإصلاح المدخلات؛ انظر [متابعة K1](reviews/k1-follow-up.md).
2. **K2:** تصميم نموذج تفويض ونطاقات ثابت وإثبات رفض الوصول بين الوكلاء وإلغاء المنح والسباقات. إلى أن يوجد مضيف وهوية موثوقة، اختبارات مكتبة واحدة لا تثبت عزل عملاء غير موثوقين.
3. **Crypto Vault:** مراجعة التصميم والاعتمادات أولًا، ثم تنفيذ التخزين المغلف مع اختبارات كلمة مرور خاطئة، تعديل ciphertext/tag/AAD، نقل سجل، تغيير كلمة المرور، تدوير DEK، فشل/تعطل، وخصوصية السجلات. يوضح الاختبار حدود حذف السجل والرجوع لنسخة قديمة.
4. **نسخ مشفر:** تصدير واستعادة فعلية بعد إغلاق العملية وعلى جهاز/عملية أخرى، والتعامل مع البيانات الكبيرة والفساد والاقتطاع والتعارض والفشل دون تلف المصدر. الاستعادة بالمفتاح وكلمة المرور المختبرتين فقط.
5. **Trusted Host والواجهة:** مصادقة وتفويض وموافقات وحماية المفاتيح واختبارات end-to-end قبل ربط واجهة العالم. لا تنشيط مزود خارجي أو تكلفة دون موافقة.

لا موعد أو تكرار مراجعة أمنية آلي مُنشأ حتى الآن. يمكن اعتماد مراجعة شهرية للتهديدات والتبعيات والمعايير والنتائج إذا حُدد مالكها وأداة التذكير.
