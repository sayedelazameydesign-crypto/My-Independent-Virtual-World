# عقد المضيف الموثوق — v2 مقترح

**غير منفذ وغير مختبر.** هذا عقد حدود وسلوك، لا خادمًا جاهزًا ولا تعديلًا لـ`ui-kernel-contract` v1. التنفيذ والربط يتطلبان مراجعة مستقلة لمصدر Lovable وبيئة التشغيل. لا تثبت أنواع TypeScript أو هوية يرسلها العميل مصادقة.

## الهوية وحدود الوصول

المضيف الموثوق ينشئ النواة والمخازن الخاصة به، ويتلقى طلبات محددة من واجهة أو عميل. يستخرج مستخدمًا من جلسة مصادق عليها، ثم يربط وكيلًا مسجلًا بمستخدمه وفق سياسة المضيف؛ العميل قد يطلب اختيار وكيل لكنه لا يستطيع فرض ملكية أو صلاحية أو اعتبار اختياره مصادقًا عليه. يتحقق المضيف من التفويض على كل عملية ووقت أثرها؛ لا وصول مباشر للمخزن الخام أو إعدادات المنح أو المفاتيح.

آلية تسجيل الدخول وإصدار جلسة أولى آمنة في الجهاز المحلي **غير محسومة** ويجب تصميمها واختبارها وفق بيئة النشر. لا تكفي loopback وحدها. على التنفيذ التحقق من Host وOrigin، ومنع CSRF وDNS rebinding، وتقييد CORS، وحماية الجلسات وXSS وCSP؛ HTTPS عند المرور عبر الشبكة، وعدم وضع الأسرار في URL أو `localStorage`. المسارات من المتصفح نسبية. معاينة بعيدة ليست جهاز المستخدم؛ لا تُنقل إليها بيانات حساسة أو تُفتح للعامة دون تقييم وموافقة.

## سياق الطلبات والرسائل والموافقات

يتضمن كل طلب داخلي معرف طلب يحدده المضيف، وفاعلًا مصادقًا عليه، ومالكًا ومساحة محددين من سياق موثوق، ونوع عملية ووجهة ونطاق بيانات، وحالة تنفيذ. يحجز المضيف هوية ونطاق الطلب قبل التنفيذ، ولا يثق بحقول `approved` أو `ownerId` أو `agentId` باعتبارها دليلًا. لا يجب أن يُنشر نص الملاحظات أو الأسرار في السجلات أو الأحداث افتراضيًا.

الرسالة المحتملة بين الوكلاء تمر لاحقًا عبر وسيط المضيف، وتحدد مصدرًا موثقًا ومستلمًا ونوعًا و`requestId` ونطاقًا وحالة. لا تُنقل بيانات مساحة أو ذاكرة أو رسالة لمستلم دون تفويض محدد. لا يُعد هذا تعريفًا لوسيط رسائل منفذ أو ضمانًا لتسليم مرة واحدة؛ سيحتاج عقد رسائل مستقلًا للاختبارات والتكرار والتعطل قبل البناء.

قرار الموافقة مرتبط بهوية الموافق، والطلب والعملية والوجهة ونطاق البيانات والتكلفة المحتملة وبصمة الحمولة وانتهاء الصلاحية؛ يستهلك مرة واحدة فقط. أي تعديل يتطلب موافقة جديدة. انتهاء أو رفض أو فشل التحقق لا يتحول إلى قبول. لا يمنح الوكيل لنفسه موافقة أو امتيازًا. إلغاء قرار أو منحة يمنع أثرًا لم يبدأ بعد وفق ترتيب المعاملة، ولا يعد بإلغاء أثر اكتمل.

## التكرار والحالة والتدقيق

حالات العمل المقترحة `queued`, `awaiting_approval`, `running`, `completed`, `denied`, `failed`, `unknown`. `failed` لفشل معروف؛ عندما قد يكون الأثر وقع دون إثبات النتيجة تكون `unknown`، وتُراجع ولا تعاد تلقائيًا. يُربط مفتاح idempotency بالهوية والعملية وحمولة محددة: إعادة نفس المفتاح والحمولة تعيد الحالة المصرح بها؛ استخدام المفتاح لحمولة مختلفة تعارض. تُسجل المطالبة والنتيجة والأثر في معاملة ذرية عند إمكان ذلك. فشل الشبكة أو العملية الخارجية لا يضمن ذرّية، فلا يُدّعى منع تكرار مطلق.

يُصمم سجل دائم محدود المحتوى: الوقت و`requestId` والفاعل الموثق والعملية ونطاق غير حساس والنتيجة والموافقة. لا كلمات مرور أو مفاتيح أو نصوص افتراضيًا؛ البصمات غير المملحة لنصوص قصيرة قد تكشف محتواها بالتخمين، لذا تُراجع حماية بصمة الحمولة والاحتفاظ ومفتاحها ضمن تصميم الأسرار قبل التنفيذ. يحدد التصميم ما يحدث عند فشل السجل قبل الأثر وبعده، مع عرض عدم اليقين إن لم تثبت النتيجة. لا يدّعي السجل مقاومة العبث.

## الوصول إلى الخزنة

عند اعتمادها لاحقًا، لا يرسل المضيف DEK أو KEK إلى الواجهة أو الوكيل. إذا أدخل المستخدم عبارة مرور في واجهة ويب تستطيع هذه الواجهة رؤيتها مؤقتًا؛ تُحدد قناة إدخال موثوقة وتُراجع مخاطرها قبل التنفيذ، ولا وعود بعزل غير موجود. حالة الخزنة وتصميمها المقترحان في [المراجعة العقدية](k2-trusted-host-contract-review.md). لا توجد خزنة منفذة هنا.
