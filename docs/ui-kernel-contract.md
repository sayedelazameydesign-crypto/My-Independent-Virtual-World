# عقد مقترح لربط الواجهة بالنواة — v1

**الحالة: تصميم غير منفذ وغير مختبر.** يتطلب مراجعة مصدر Lovable واختيار بيئة تشغيل موثوقة قبل الاعتماد. لا يصف endpoints موجودة اليوم ولا يخول الواجهة الوصول المباشر إلى SQLite أو الأسرار أو إعدادات صلاحيات النواة.

## حدود الثقة

```text
واجهة العالم في المتصفح
      │  نفس الأصل + جلسة مصادقة محمية
      ▼
مضيف محلي موثوق: هوية + صلاحيات + موافقات + إدارة تشغيل
      │  مدخلات محققة وهوية يحددها المضيف
      ▼
Kernel  →  مخزن يملكه المضيف
```

- المضيف ينشئ النواة ويملك إعداداتها ومخزنها؛ المتصفح يعرض الحالة ويرسل طلبات بيانات محددة فقط. SQLite من `node:sqlite` في عملية Node ولا يُستورد في حزمة المتصفح. لا وصول من الواجهة مباشرة إلى خدمة محلية أو ملف قاعدة البيانات.
- يعمل المضيف محليًا دون اتصال خارجي افتراضيًا. تُستخدم مسارات نسبية مثل `/api/v1/...` حتى لا يشير كود المتصفح إلى `localhost` ثابت؛ في معاينة بعيدة قد يكون المضيف في بيئة المعاينة لا جهاز المستخدم، فتُعرض هذه الحقيقة ولا تُستخدم بيانات شخصية قبل مراجعة الأمان.
- لا تكفي الواجهة أو حلقة loopback وحدها للمصادقة. يُنشئ المُشغّل المحلي الموثوق جلسة خاصة، مع تحديد آلية توزيعها وحمايتها وفق بيئة الإطلاق قبل التنفيذ؛ لا أسرار في URL أو التخزين المحلي للمتصفح. تحقق الخادم من `Host` و`Origin`، وحماية CSRF لطلبات التغيير، وجلسات محدودة وآمنة، وسياسة CSP، وتقييد CORS. HTTPS عند عبور الشبكة؛ لا فتح عام أو تجاوز معاينة آمن افتراضيًا دون مصادقة.
- هوية المستخدم والوكيل المصرح بهما مشتقة من جلسة المضيف وسياقها، لا من `agentId` يقدمه العميل. تتقرر ملكية الملاحظات ونطاقات الوصول قبل دعم عدة مستخدمين أو وكلاء؛ لا تُستخدم المعرفات المتسلسلة كأسرار.

## أشكال الرسائل المقترحة

كل طلب JSON يستخدم مخططًا مضبوطًا يرفض الحقول الزائدة، ويحد الحجم وعدد الخطوات وطول المحتوى قبل الوصول للنواة. كل نتيجة تحمل `requestId` وحالة ومخططًا بإصدار ثابت؛ لا تعرض استثناءات داخلية أو مفاتيح. العناوين والاستجابات أدناه تصور أولي، وليس API موجودًا.

| العملية | الطلب | الاستجابة والسلوك |
|---|---|---|
| معلومات الحالة | `GET /api/v1/status` | حالة المضيف والمخزن (`persistent` أو `volatile` أو `unavailable`) وقدرات مثبتة فقط، دون أسرار أو محتوى. |
| تقديم خطة | `POST /api/v1/runs` مع `Idempotency-Key` وخطة أفعال مقبولة | `202` مع `requestId` وحالة أولية؛ يتحقق المضيف من الجلسة والهوية والصلاحيات، ويحفظ بصمة الحمولة ومفتاح الطلب قبل الأثر. لا `agentId` أو `approved` من العميل. |
| قراءة حالة | `GET /api/v1/runs/{requestId}` | النتيجة المسموح للجلسة برؤيتها، مثل `queued` أو `awaiting_approval` أو `running` أو `completed` أو `denied` أو `failed` أو `unknown`. `unknown` يعني أن الأثر غير محسوم ولا يُعاد تلقائيًا. |
| قرار موافقة | `POST /api/v1/approvals/{approvalId}/decision` | `approve` أو `deny` فقط من جلسة مخولة؛ قبل التنفيذ يطابق الخادم القرار بالعملية المجمّدة والهوية ونطاق البيانات، ويستهلكه مرة واحدة قبل انتهاء صلاحيته. |

مثال توضيحي لطلب إنشاء خطة؛ لا يتضمن هوية أو علم موافقة:

```json
{"version":1,"actions":[{"kind":"notes.create","text":"ملاحظة"}]}
```

مثال حالة انتظار تعرض للواجهة ما يجب أن يفهمه المستخدم قبل الموافقة:

```json
{"version":1,"requestId":"run-id","status":"awaiting_approval","approval":{"id":"approval-id","action":"notes.create","destination":"local-store","dataSummary":"ملاحظة","expiresAt":"2026-11-07T12:00:00Z"}}
```

المعرفات والأوقات هنا أمثلة شكلية وليست معرّفات حقيقية. إذا تعذر عرض البيانات المطلوبة للموافقة بأمان، يُرفض الطلب. لا تحفظ أو تسجل الملخصات الحساسة تلقائيًا. للقراءة يتأكد المضيف من نطاق الوصول إلى الملاحظة قبل إرجاع محتواها؛ لا يجعلها متاحة بمجرد معرفة معرفها.

## الموافقة والتكرار والفشل

- تتحقق الموافقة من الجلسة وصلاحية المُفوِّض، ونوع الإجراء، والوجهة، ونطاق البيانات والتكلفة المحتملة؛ يربطها الخادم ببصمة الحمولة والهوية والانتهاء ومعرّف منفرد. التغيير يتطلب موافقة جديدة. رفض أو انتهاء أو تعطل لا يتحول إلى قبول.
- لتجنب تكرار الأثر، يحفظ المضيف مفتاح التكرار والحمولة والنتيجة لكل هوية في سجل دائم. إعادة المفتاح مع الحمولة نفسها تسترجع الحالة؛ مع حمولة مختلفة تُرفض. يجب تسجيل استهلاك الموافقة والأثر والنتيجة ذريًا متى كان ذلك ممكنًا؛ إذا تعذر إثبات النتيجة بعد التعطل تكون `unknown` ويتطلب الأمر مراجعة، لا إعادة عمياء.
- `400` للمدخل غير الصالح، `401` لجلسة غير مصادق عليها، `403` لرفض الصلاحية، `409` لتعارض التكرار أو الحالة، `429` لتجاوز الحدود، و`503` لعدم توفر المخزن. لا تظهر تفاصيل حساسة؛ يُسجل الحد الأدنى ويُختبر فشل السجل. اختيار الأكواد وتنفيذها مؤجلان للتحقق من إطار المشروع.
- السجل المنشود يحتوي معرّفات غير حساسة والوقت وهوية مصادقًا عليها ونوع العملية ونتيجتها، دون محتوى أو رموز أو مفاتيح افتراضيًا، مع سياسة احتفاظ محدودة. لا يوصف سجل النموذج المؤقت بأنه تدقيق دائم.

## الذاكرة والنسخ

توضح الواجهة ما إذا كان التخزين دائمًا أو مؤقتًا أو غير متاح، ولا تنتقل إلى الذاكرة دون تحذير وموافقة مناسبة. تصدير واستعادة النسخ عمليتان منفصلتان للمستخدم المصرح له؛ تعرض الواجهة التحذير من plaintext والوجهة وتطلب موافقة. لا تقبل الواجهة مسار ملف اعتباطيًا للتنفيذ على المضيف. الاستعادة الحالية إلى مخزن فارغ فقط؛ أي دمج أو استبدال يحتاج عقدًا واختبارات منفصلين.

## بوابات قبول الربط

- اختبارات مصادقة وانتحال وCSRF وOrigin/Host، وإثبات تعذر الوصول إلى المخزن والأسرار مباشرة من الواجهة.
- اختبارات هوية وصلاحيات على مستوى الموارد، ورفض وتعديل وانتهاء الموافقة، والتكرار والسباقات والتعطل والنتيجة المجهولة.
- اختبارات متصفح فعلية لتشغيل الواجهة العربية/الإنجليزية، واستمرار البيانات بعد إعادة التشغيل، والتصدير والاستعادة والفشل، دون ادعاء نجاح لمشروع Lovable قبل وصوله.
- نجاح اختبارات البناء على المصدر الفعلي وCI بعد إعداده إن اعتُمد، وتوثيق التكلفة والتبعيات ونتائج الاختبارات التي تعذر تنفيذها. لا تكامل مدفوع أو إرسال خارجي دون موافقة مسبقة.
