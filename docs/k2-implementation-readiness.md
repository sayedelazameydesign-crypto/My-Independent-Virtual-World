# مراجعة جاهزية تنفيذ K2 والمضيف الموثوق

## القرار

**NO-GO لتنفيذ الأمان أو التشفير أو ربط الواجهة حاليًا.** هذه مراجعة قبل كتابة أول ملف تنفيذي لـK2؛ تحدد ما يجب اعتماده وما يجب إثباته، ولا تعلن حل R1–R7 أو وجود مصادقة أو عزل. النواة الحالية وSQLite وواجهات v1 باقية كما هي. لا مصدر Lovable أو CI موثوق مثبت في هذه المراجعة.

## 1. حدود التنفيذ المقترحة

```text
عميل غير موثوق → Trusted Host v2 → بوابة مصادقة/سياسة/موافقة
                                      │
                                      ▼
                        خدمة ذاكرة مقيّدة + تخزين v2 خاص
```

- المضيف يثبت المستخدم ويربط الوكيل المسجل بسياقه؛ `ownerId` و`agentId` والأنواع التي تأتي من العميل ليست هوية مثبتة. تُفرض المنحة على المورد عند الأثر، لا بمجرد دخول الواجهة. تفاصيل ربط الجلسة الأولى بالجهاز وحمايتها من الاستيلاء والخروج الآمن **مفتوحة**.
- المسار المفضل خدمة v2 مستقلة؛ لا يُمرر `NoteStore` القديم بلا سياق باعتباره مخزنًا معزولًا، ولا يُعرض `Kernel.run(agentId, input)` أو المخزن الخام إلى العميل. محول لربط Kernel القديم اختياري فقط بعد إثبات شروط [R1](k2-review-fixes.md). لا تغيير لواجهات v1 أو fallback إليها عند رفض v2.
- الحد الأمني يفترض مضيفًا ونظام تشغيل موثوقين، وليس عزل كود خبيث داخل العملية. عند النشر خارج الجهاز يلزم تقييم مصادقة ونقل منفصل؛ لا يُفترض أن بيئة المعاينة جهاز المستخدم. لا خدمات مدفوعة أو اتصال سحابي مطلوب افتراضيًا.

## 2. مخطط بيانات مفاهيمي v2 — غير منفذ

الكيانات التالية اقتراح مراجعة، وليست أوامر SQL أو ترحيلًا. تُراجع التفاصيل والتراخيص والأداء قبل البناء.

| الكيان | الحقول الأساسية | القيود المطلوبة |
|---|---|---|
| مستخدم وهوية مضيف | معرف داخلي وحالة حساب/جلسة | إثبات الهوية يصدره المضيف لا سجل يختاره العميل؛ دورة الجلسة وتخزين أسرارها لا تزال مفتوحة. |
| وكيل | معرف داخلي، مالك وحالة | ربط فريد بمالك مثبت؛ لا انتحال أو تمكين ذاتي. |
| مساحة | معرف، مالك، حالة/نوع | مالك واحد؛ مساحة مشتركة لا تفتح بقية مساحات المالك. |
| سجل | معرف، مالك، مساحة، نوع، مراجعة ومحتوى | سلامة علاقة المالك بالمساحة، ومعرف فريد ومراجعة تمنع الكتابة المتعارضة. البحث والقوائم يحترمان النطاق. |
| منحة | معرف، مالك، وكيل، عملية، نطاق مساحة أو سجل، حالة/انتهاء اختياري | تطابق مالك الوكيل والنطاق، وفصل `read` و`create` و`update` و`delete`، ورفض افتراضي؛ `create` على مساحة. المنح المستعادة لا تُفعّل تلقائيًا. |
| طلب/موافقة | معرف طلب وهوية ونطاق وبصمة حمولة وحالة، ومعرف موافقة وانتهاء وقرار | المنحة مستقلة عن الموافقة؛ القرار أحادي الاستخدام ومربوط بطلب ثابت. بصمة الطلب تحتاج تصميم سر HMAC وسياسة مفاتيح. |
| سجل تدقيق | وقت مؤهل وطلب وفاعل ونطاق غير حساس ونتيجة | لا محتوى أو أسرار افتراضيًا؛ فشل الحجز قبل الأثر الحساس يمنع الأثر. سجل مضاد للتلاعب لم يُثبت. |

قبل اعتماد DDL: تثبيت المعرفات والمفاتيح والقيود المركبة والفهارس، ومتى تُحذف أو تحفظ كل علاقة، وقيود المساحة والسجل والمنحة، وسياسة `revision`، ومخطط الإصدارات والترحيل. يجب اختبار تفعيل القيود في SQLite فعلًا، وعدم الاكتفاء بتعريف TypeScript أو فحص واجهة. لا يحقق المخطط وحده عزل ملفات قاعدة البيانات عن عملية مضيف مخترقة.

### حدود المعاملات

الأثر المحلي وإبطال المنح وحجز الموافقة وسجل النية ونتيجة idempotency تُرتب ضمن حدود معاملة يمكن إثباتها. إلغاء ملتزم أولًا يمنع أثرًا لم يبدأ؛ عملية ثبتت أولًا لا يُسترجع ما كشفته. فشل حجز سجل التدقيق يمنع بدء الأثر الحساس؛ إن حدث أثر ثم تعذر إثبات نتيجته فالنتيجة `unknown` ويُمنع التكرار الأعمى. أثر خدمة خارجية لا يصبح ذريًا بمجرد وجود معاملة محلية. لا منحة تتجاوز موافقة مطلوبة، ولا موافقة تنشئ منحة مستمرة.

## 3. قرار الوقت بعد إعادة التشغيل أو الاستعادة

**الافتراضي المحدد للتنفيذ الأول المقترح:** عند بدء المضيف أو استعادة معروفة، تبدأ حالة الثقة الزمنية `unverified`، ولا تُستخدم ساعة النظام أو قيمة محفوظة في قاعدة قابلة للاستعادة وحدهما لإثبات الوقت. تُرفض/تؤجل جميع المنح محددة الزمن والموافقات الزمنية حتى ينجح تحقق مستقل معتمد؛ لا تُحوّل إلى منح بلا انتهاء. الموافقات المعتمدة مسبقًا لا تستعاد تلقائيًا. تبقى المنح المستعادة في الحجر إلى إعادة منح صريحة وفق R3، بما فيها غير المحددة بزمن.

خلال تشغيل واحد يمكن استخدام ساعة رتيبة لقياس مدد **بعد** تثبيت مرجع زمن موثوق، مع حدود لانحرافه وفترة صلاحيته. هذه الساعة لا تعطي UTC ولا تثبت الزمن عبر إعادة التشغيل. ملاحظة أن ساعة النظام لم تتراجع مقارنة بقيمة داخل القاعدة ليست دليلًا ضد rollback، والساعة الرتيبة وحدها لا تثبت أن UTC صحيح.

مصدر الوقت الموثوق نفسه **لم يُختَر أو يُنفذ**. لقبول أي مصدر لاحقًا يلزم توثيق حد ثقته ومصدره، وأصالة الدليل وحداثته ومقاومة إعادة تشغيله، ومرجع ثقة مستقل غير قابل للإرجاع بالنسبة إلى البيانات المستعادة، وحد أقصى للانحراف والعمر، وسلوك فقدان المصدر. قد يكون مصدرًا محليًا مستقلًا أو خدمة اختيارية بعد الموافقة؛ لا نفترض توفر عتاد أو مزود مجاني أو خدمة سحابية. إذا كان المرجع قابلًا للنسخ مع القاعدة أو لا يثبت حداثته فلا يُعد تحققًا. إدخال المالك وقتًا يدويًا وحده ليس دليلًا تقنيًا موثوقًا؛ لا يُفعّل السياسة تلقائيًا.

**الأثر العملي:** النسخة المحلية دون مصدر تحقق مقبول ستبقى رافضة للعمليات الزمنية بعد إعادة التشغيل. اختيار المصدر وآلية التحقق والأرقام والاختبار على بيئة حقيقية بوابة مفتوحة؛ ليست حالة `verified` أو اكتشاف تراجع خفي ميزة موجودة الآن. يعالج هذا سياسة الفشل الافتراضي لكنه لا يثبت توفر مصدر وقت.

## 4. عقود التنفيذ والترحيل

- مدخل المضيف يستقبل بيانات محددة شبيهة JSON ومحدودة الحجم؛ يتحقق من الهوية والسياق ويُصدر سياقًا داخليًا للذاكرة المقيدة. `AccessContext` TypeScript قابل للتزوير ولا يكفي دليلًا؛ يُطبق التفويض في نقطة الوصول والمعاملة. المنحة والقرار لا يثق بهما من حقول العميل.
- `ScopedNoteStore` تصميم جديد مستقل عن `NoteStore`; عمليات القراءة والإنشاء أولًا، والتعديل والحذف غير منفذين. لكل مورد تحقق ملكية ومساحة ومنحة وحالة الخزنة عند وجودها، ومنع الوصول الخام خارج المضيف.
- الترحيل من SQLite أو JSON v1 يتطلب مصادقة وتأكيد ملكية المجموعة أو ربطًا يدويًا، ولقطة متسقة تشمل WAL ونسخة plaintext قابلة للاستعادة، ثم هدفًا منفصلًا يتحقق منه قبل تفعيل بموافقة مستقلة. لا يُحذف الأصل أو يفعّل منحًا تلقائيًا. اختبارات الترحيل والاستعادة غير منفذة.
- في استعادة معروفة تُحجر المنح والجلسات والموافقات ويعاد المنح صراحة بعد مصادقة. استعادة ملفات خفية أو clone لا يمكن اكتشافها من قاعدة يمكن إرجاعها وحدها؛ مرجع freshness مستقل مطلوب قبل الادعاء بحمايتها. لا يُدّعى تشفير أو نسخ مشفرة.

## 5. الاختبارات والبوابات قبل ربط الواجهة

[مصفوفة K2](k2-acceptance-matrix.md) هي حالات قبول مقترحة وليست نتائج. قبل البناء تُحوّل إلى اختبارات قابلة للتكرار تغطي:

1. **توافق v1:** الاختبارات القديمة والبناء و`typecheck` دون تغيير API أو صيغة `mivw.notes` v1؛ لا يدل نجاحها على أمان v2.
2. **هوية وعزل:** مستخدمان ووكيلان، انتحال السياق، قراءة وإنشاء خارج النطاق، صلاحيات منفصلة، ومساحة مشتركة محددة؛ اختبارات على خدمة ومضيف فعليين لا mock فقط.
3. **موافقة وإلغاء:** منحة موجودة مع غياب موافقة **تشترطها السياسة** تُرفض؛ موافقة دون منحة لازمة تُرفض؛ وقراءة أو عملية v2 مستقبلية لا تشترط السياسة لها موافقة قد تمضي بمنحة صالحة وبقية الشروط؛ إنشاء v1 يحتفظ بشرط `approveCreate`. سباقات الموافقة والإلغاء تُختبر بمعاملات قابلة للتكرار.
4. **وقت واستعادة:** بدء/إعادة تشغيل أو استعادة دون دليل وقت → `unverified` ورفض العمليات الزمنية، تراجع/انقطاع/دليل غير موثوق أو معاد تشغيله، واستعادة معروفة لمنحة ملغاة تبقى غير فعالة. اختبار مرجع freshness فعلي قبل إعلان كشف rollback خفي.
5. **تدقيق وتكرار وترحيل:** فشل حجز التدقيق قبل الأثر، غموض ما بعد الأثر، نفس المفتاح ونفس/حمولة أخرى، فقد مفتاح البصمة، ونسخة WAL وفشل كل خطوة مع بقاء الأصل قابلًا للاستعادة.
6. **تشغيل موثوق:** مراجعة آلية الجلسة، اختبارات Host/Origin وCSRF وXSS والواجهة الحقيقية، وCI مستقل بعد إعداده؛ لا يُعد mock أو نتيجة محلية سابقة إثباتًا لاختبار التكامل.

## 6. قائمة قرار التنفيذ

| القرار | الحالة |
|---|---|
| السياسة الافتراضية للوقت عند فقد الدليل | محددة تصميميًا: `unverified` ورفض/تأجيل العمليات الزمنية |
| مصدر وقت موثوق ودليله المستقل | **مفتوح؛ مانع لتفعيل المنح والموافقات الزمنية** |
| مرجع كشف rollback الخفي | **مفتوح؛ لا ادعاء حماية** |
| هوية الجلسة الأولى والمضيف الموثوق | **مفتوح؛ لا ربط واجهة** |
| مفتاح HMAC، مخزن الأسرار، الإصدار والتدوير والاحتفاظ | **مفتوح** |
| DDL v2 والمعاملات وخطة الترحيل المختبرة | **مفتوح** |
| تنفيذ K2 وCI واستعادة Lovable | **غير منفذ/غير مثبت** |
| Crypto Vault وnonce والنسخ المشفرة | **مؤجل** |

بعد مراجعة واعتماد هذه القرارات يمكن تكليف تنفيذ محدود تدريجي، مع إبقاء ما لا يملك دليلًا موثوقًا مغلقًا؛ لا يشكل هذا المستند إذنًا بتعديل `main` أو إنشاء خدمة خارجية.
