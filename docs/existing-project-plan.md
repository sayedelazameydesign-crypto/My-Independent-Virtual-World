# خطة تنفيذ المشروع القائم — MIVW

## الحالة والقرار

المستخدم أفاد بوجود مشروع Lovable مبني بـReact وTypeScript، وبأن آخر commit معروف هو `0436919f1a51d0e4d0e6080f374f6146f9d1806d` وأن البناء لم ينجح. هذه معلومات **لم نتحقق منها في المصدر بعد**. يحتوي المستودع الحالي على وثائق ونموذج نواة مستقل أُنشئ بموافقة المستخدم؛ لم يصل رابط مستودع المشروع الفعلي أو أرشيفه حتى الآن. لم يُدمج النموذج مع المشروع. لا توجد نتائج بناء أو اختبارات يمكن إعلانها.

القرار: استكمال المصدر القائم بأقل تغيير ممكن عند وصوله، لا إنشاء مشروع بديل أو فرض إعادة كتابة. أجاز المستخدم بناء [نموذج نواة مستقل](../packages/kernel/README.md) الآن؛ يُراجع توافقه قبل أي دمج. مسار Python/SQLite القديم كان اقتراحًا قبل معرفة المشروع القائم، وليس تكليفًا معتمدًا له. لا رصيد مدفوع ولا قاعدة سحابية أو نشر أو ربط حساب تلقائيًا.

## المرحلة 0 — استلام المصدر وتثبيت خط الأساس

**المدخل:** رابط مستودع GitHub قابل للقراءة أو ZIP يحتوي المشروع، دون أسرار أو `node_modules`. يفضل مستودع Git للتحقق من التاريخ؛ لا يثبت ZIP وجود commit أو صحته.

- فحص المصدر في مساحة منفصلة دون الكتابة فوق ملفات هذا المستودع أو تغيير مشروعات أخرى. التحقق من اسم المصدر والفرع والشجرة والـcommit الكامل عند توفر Git، وعرض أي اختلاف عما أبلغ به المستخدم.
- فحص الملفات وإعدادات البناء وأوامر `package.json` وملف القفل وإصدار Bun أو Node المطلوب و`AGENTS.md` والتراخيص. لا نفترض أن أسماء الملفات أو الأوامر المبلغ عنها موجودة أو صالحة قبل رؤيتها.
- مراجعة الأوامر والسكريبتات والتبعيات قبل تشغيلها؛ لا نكشف أي أسرار أو نشغّل سكريبتات غير موثوقة دون مراجعة. استخدام تثبيت بقفل ثابت ودون سكريبتات تثبيت حيث تسمح الأدوات، وتوثيق أي تعذر. لا تفعيل لخدمات خارجية أو تغيير إعدادات الحسابات.
- إجراء الفحوص في نسخة معزولة: تتوقع تثبيت التبعيات وملفات مخرجات مؤقتة، لكنها لا تعدل المصدر الأصلي. ZIP يُفحص قبل الاستخراج لمنع المسارات الخارجة عن المجلد والروابط غير الآمنة.

**المخرج:** تقرير مصدر موثّق وخط أساس للتبعيات والقدرات وحالة التحقق. تُسجل القيود بدل الافتراض عند عدم توفر تاريخ Git أو بيئة التشغيل.

## المرحلة 1 — تشخيص بلا تعديل على المصدر

بعد مراجعة تعريف الأوامر وتجهيز التبعيات، تُشغّل إن كانت موجودة ومناسبة:

```text
bun run build
bun run lint
bun run test
bunx tsc --noEmit
```

يُستخدم TypeScript المثبت من قفل المشروع، ولا يُحمّل إصدار جديد تلقائيًا لمجرد نجاح `bunx`. إذا غاب أمر أو أداة، يُسجل «غير متاح» وسبب ذلك؛ لا يُضاف سكريبت لمجرد تحويل النتيجة إلى نجاح. تُفحص إعدادات الاختبار وما إذا كان الأمر ينتهي أو يدخل وضع المراقبة، ويُستخدم بديل غير تفاعلي موثق عند الحاجة. لكل أمر: الإصدار، النتيجة ورمز الخروج، ورسائل الخطأ الجوهرية.

**بوابة المراجعة:** تقديم الأخطاء الفعلية، وأسبابها المحتملة، والملفات المتأثرة، وأصغر تغييرات مقترحة، وما لم يُختبر. **التوقف لانتظار موافقة المستخدم قبل تنفيذ الإصلاحات.**

## المرحلة 2 — إصلاح البناء بعد الموافقة

- تنفيذ التغييرات المتفق عليها فقط، دون إضافة ميزات أو إعادة تصميم أو تبديل المكدس. الحفاظ على السلوك المقصود قدر الإمكان وعدم إخفاء الأخطاء بإزالة الاختبارات أو تعطيل قواعد TypeScript أو Lint.
- إعادة الفحوص الأربعة مع تسجيل النتائج. إذا تعذر أحدها يُذكر ذلك صراحة مع السبب، ولا يعتبر ناجحًا.
- مراجعة الفروقات والتبعيات والتراخيص، وتحديث تعليمات التشغيل بحسب ما تحقق فعليًا.
- **القبول:** نجاح الأوامر الموجودة بصورة قابلة للتكرار، أو تقرير صريح بما يمنع النجاح. النجاح التقني للبناء لا يثبت عمل الذاكرة أو الوكلاء أو الواجهة المرئية.

## المرحلة 3 — إثبات الذاكرة والنسخ الاحتياطي

فحص تنفيذ IndexedDB والبديل المؤقت الموجودين في المصدر، لا استبدالهما مسبقًا. اختبار إنشاء وتعديل وحذف البيانات، وإعادة تحميل الصفحة وإعادة فتح التطبيق في متصفح حقيقي، إلى جانب اختبارات الوحدة. تُوضح حدود بيانات المتصفح وسياسة مسحها؛ `fake-indexeddb` وحده لا يثبت الدوام الفعلي.

- عند رفض التخزين أو امتلائه أو تعذره، يظهر خطأ واضح؛ لا يُقدَّم التخزين المؤقت على أنه دائم، ولا يُستخدم دون إظهار طبيعته ومخاطر فقده.
- اختبار تصدير واستعادة البيانات في نسخة اختبار، مع التحقق من الصيغة والإصدار والتعارضات والنسخة التالفة، وحماية البيانات الحالية من الفقد أو الاستعادة الجزئية الصامتة. لا تُصدَّر الأسرار؛ تُحذر الواجهة إذا كانت النسخة غير مشفرة.
- **القبول:** نتائج موثقة للنجاح والفشل والاستعادة الفعلية؛ لا ادعاء بوجود مزامنة أو نسخة سحابية تلقائية.

## المرحلة 4 — Kernel والقدرات الحقيقية

تُفحص البنية الحالية أولًا، ثم تُعرّف حدود بسيطة للطلبات والنتائج والحالة والأذونات وسجل أحداث محدود البيانات. تمر الأفعال عبر Kernel بدل وصول الواجهة المباشر إلى الأدوات والمزودين. يبدأ محرك الوكلاء بدورة Understand → Plan → Act → Observe → Reflect، مع اختبار تنفيذ فعلي محدود، وحالات فشل وإيقاف؛ لا يُعد تعريف الوكيل تنفيذًا له.

**حد أمني:** Kernel يعمل داخل المتصفح وحده ليس حدًا أمنيًا موثوقًا لحماية الأسرار أو عزل الكود. قبل أي صلاحية حساسة يلزم تصميم طبقة تشغيل موثوقة منفصلة، مع ضبط الصلاحيات والموافقات والتحقق من الطلبات. لا تشغيل أوامر عامة أو إرسال خارجي تلقائي.

**القبول:** اختبار تدفق طلب إلى نتيجة وحالة فشل وموافقة مرفوضة، دون وصف المحاكاة بأنها وكيل يعمل فعليًا.

## المرحلة 5 — الذكاء والتكاملات

- بناء عقد مزود محايد ثم فحص محول محلي اختياري مناسب للموارد والتراخيص، دون تنزيل نموذج أو تشغيل خدمة مدفوعة تلقائيًا. الاختبارات الوهمية تُسمى كذلك؛ نجاح مزود اختبار لا يثبت اتصال نموذج حقيقي.
- إخفاق المزود يُظهر عدم التوفر أو بديلًا مفعلًا ومصرحًا به، دون تسريب بيانات أو رسوم مفاجئة. لا ضمان دائم لمجانية أي مزود.
- إضافة GitHub وDrive وغيرهما فقط بعد فحص التراخيص والواجهات والحصول على الموافقة على الوجهة والبيانات والصلاحيات؛ يبقى تشغيل النواة غير معتمد عليها. تبقى مشروعات CeliaOS وphone-google وdr.mukhtar مستقلة.
- **القبول:** إثبات اتصال فعلي مأذون ورفض/فشل وصلاحيات مناسبة، أو توثيق أن الاختبار الفعلي غير منفذ. لا تصل أسرار المزودين إلى الواجهة أو النسخ الاحتياطية أو Git.

## المرحلة 6 — العالم المرئي والإصدار

توصيل واجهتي 2D/3D بالحالة الحقيقية للنواة بعد إثباتها، مع مراعاة العربية وRTL وإمكانية الوصول، وتوفير بديل واضح عند تعذر العرض ثلاثي الأبعاد. تُختبر الإجراءات والحالات في متصفح فعلي، ويُعلن ما لم يُختبر. يشمل تقرير الإصدار أوامر التشغيل والفحوص والقيود وتراخيص التبعيات.

## دمج المصدر والتاريخ

لا يثبت وصول ZIP تاريخ Git. قبل نقل المصدر إلى هذا المستودع، تُعرض خطة الاستيراد والفروقات ومخاطر تعارض ملفات التوثيق الحالية للحصول على الموافقة. لا يُستبدل `.git` ولا يُحذف تاريخ المستودع الحالي، ولا تُدفع تغييرات أو تُفتح طلبات دمج تلقائيًا. الحفاظ على تاريخ المصدر الكامل يتطلب وصولًا فعليًا إلى مستودع Git أو bundle ومراجعة استراتيجية الدمج؛ لا يُفترض أن نسخ الملفات يحفظ التاريخ.
