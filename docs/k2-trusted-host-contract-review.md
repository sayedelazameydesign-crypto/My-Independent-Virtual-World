# المراجعة العقدية لـK2 والمضيف الموثوق

## القرار والنطاق

هذه مراجعة تصميمية لـ`1d1c404` وليست تنفيذًا أو اعتمادًا نهائيًا. **لا بدء لتشفير السجلات أو ربط Lovable** حتى تُراجع عقود الهوية والملكية ودورة الخزنة، وتُحسم نقاط التشفير أدناه. النواة الحالية لا تصادق على الهوية، ولا تعزل الوكلاء، وSQLite وJSON غير مشفرين. `main` خارج نطاق العمل.

المراجع: [العقود العامة](contracts.md)، [عقد الواجهة](ui-kernel-contract.md)، [تصميم الخزنة](vault-and-memory-design.md)، و[مراجعة النواة التاريخية](reviews/kernel-security-e84c96e.md). عند اختلاف التفاصيل، هذا المستند **اقتراح لتحديث العقود** وليس دليلًا على تغيير التنفيذ.

## نموذج K2: الملكية والتفويض

### الكيانات والعلاقات المقترحة

- **المستخدم:** مالك مصادق عليه من المضيف؛ لا يثبت `userId` المرسل من المتصفح الهوية.
- **الوكيل:** معرف داخلي يربطه المضيف بمستخدم؛ لا يثبت `agentId` في `Kernel.run` الحالي هوية أو ملكية. لا يختار الوكيل سياقه أو يمنح نفسه صلاحيات.
- **المساحة:** نطاق مملوك لمستخدم واحد، مستقل عن المساحات الأخرى. المساحة المشتركة اختيارية وينشئها المالك؛ لا تعني مشاركة كل ذاكرته.
- **السجل:** `recordId` ثابت، و`ownerId` و`spaceId` و`recordType` و`revision` وإصدار مخطط، يحددها أو يتحقق منها المضيف/المخزن. تطابق ملكية السجل والمساحة شرط سلامة؛ لا تُعد المعرّفات السرية وسيلة تفويض.
- **المنحة:** المالك المصرح له يحدد الوكيل والعملية ونطاق مساحة أو مورد؛ عمليات `read` و`create` و`update` و`delete` مستقلة. التعريف لا يعني أن التعديل والحذف متاحان في التنفيذ الحالي. لا إنشاء أو تعديل أو إلغاء منحة بمجرد تقديم هوية من العميل.

القرار الافتراضي **رفض**؛ لا صلاحية موروثة أو مساحة مشتركة ضمنية. يحق للمالك إدارة موارده عبر مضيف مصادق عليه؛ تُحدد العمليات الحساسة التي تتطلب موافقة صريحة وفق سياسة المضيف. لا يحصل الوكيل على أي ملاحظة من مستخدم أو وكيل آخر إلا بمنحة صريحة مناسبة. لا تُعرَض في الأخطاء معلومات تكشف وجود مورد غير مصرّح به.

### التفويض وإلغاء المنح

1. يستخرج المضيف المستخدم الموثق ويحدد الوكيل المصرح له من سياق جلسة موثوق، ثم يتحقق من صحة الطلب والنطاق المطلوب.
2. يقرر المضيف امتلاك المورد والمنحة والعملية، ثم يطبق سياسة الموافقة. لا يكفي إخفاء زر أو قبول قرار من الوكيل نفسه.
3. يُعاد فحص المنحة عند الأثر الفعلي، وتُنفذ عملية محلية مع تحديث سجل الطلب ضمن معاملة أو تنسيق يحدد ترتيبها مع الإلغاء. إذا تم الإلغاء أولًا فلا يبدأ أثر لاحق؛ إن أُكملت العملية أولًا فالإلغاء لا يسترجع ما سبق إظهاره أو نسخه. إذا تعذر تحديد ترتيب عملية خارجية تُعرض `unknown`.
4. لا يُعد تطبيق السياسة داخل عملية JavaScript عزلًا لكود خبيث داخل العملية نفسها. المصادقة وعزل العملاء يتطلبان مضيفًا وحدود تشغيل موثوقين وتقييمًا مستقلًا؛ مشاركة DEK للمساحة لا تخلق عزلًا تشفيريًا بين الوكلاء.

## عقد NoteStore المقترح وحدود الثقة

التوقيعات التالية **مفاهيمية** وليست API منفذة: يتلقى المخزن سياقًا داخليًا مصرحًا به من المضيف، ومعرّف مساحة/سجل وإصدارًا متوقعًا عند التعديل، ويعيد نتيجة محددة أو فشلًا واضحًا. لا يأخذ صلاحيات خامًا من الواجهة. يُفضل تطبيق قيد المالك/المساحة في الاستعلامات والمعاملة نفسها لا في الواجهة وحدها. تدعم السجلات الحالية القراءة والإنشاء فقط؛ `update` و`delete` والمنح تتطلب تصميمًا واختبارات قبل الإضافة.

| العملية المقترحة | الشروط والنتيجة |
|---|---|
| إنشاء | هوية وسياق مساحة ومنحة `create`، وموافقة عند تطلب السياسة؛ يربط التخزين المالك والمساحة ويتحقق من سلامة العلاقة. |
| قراءة | تفويض `read` على المورد المحدد؛ لا يُعاد المحتوى عند الرفض أو القفل أو خطأ التحقق. |
| تعديل/حذف مستقبلًا | تفويض منفصل، وموافقة حيث تطلب السياسة، وإصدار متوقع لتجنب فقد تحديث صامت؛ نتيجة التعارض واضحة. |
| منح/إلغاء | إجراء للمالك الموثق فقط، محدد النطاق والعملية؛ رفض افتراضي وتسجيل الحد الأدنى. |

يجب أن يعبر كل مسار علني، بما فيه البحث والتصدير والاستعادة، بوابة صلاحيات المضيف. أصحاب كائن مخزن منخفض المستوى موثوقون؛ لا تُسلّم هذه الواجهة إلى الوكيل أو الواجهة ولا يُدّعى أن الكتابة المباشرة إليها تمر بالحوكمة.

## Trusted Host: هوية وعمليات وموافقات

- جلسة مصادق عليها ومحددة المدة، وهوية وكيل يحددها المضيف؛ وسيلة إصدار الجلسة المحلية وحمايتها من XSS وCSRF وDNS rebinding وطلبات أصول غير موثوقة تُراجع حسب بيئة التشغيل. الواجهة تستخدم مسارات نسبية ولا تخزن أسرارًا أو مفاتيح في `localStorage` أو URL.
- تعيين `requestId` لكل طلب وربطه بالهوية والنطاق ونوع العملية وحالتها. التسلسل المقترح: `queued` → `awaiting_approval` عند الحاجة → `running` → `completed` أو `denied` أو `failed` أو `unknown`. `failed` تعني فشلًا معلومًا؛ عند عدم اليقين بشأن الأثر تستعمل `unknown`، مع استعلام/تسوية مناسبة لا إعادة تلقائية.
- للموافقة معرّف ومالك وجلسة ونطاق ووجهة وملخص بيانات وتكلفة محتملة وبصمة حمولة ووقت انتهاء. يُستهلك القرار مرة واحدة بعد التحقق من صلاحية الموافق؛ أي تغيير في الطلب يستلزم موافقة جديدة. الرفض أو انتهاء المهلة رفض؛ لا تُستخدم الموافقة لتفويض آخر.
- مفتاح idempotency مع هوية وبصمة حمولة: تكرار المفتاح لنفس الطلب يعيد الحالة/النتيجة المصرح بها، وتكراره لحمولة مختلفة تعارض. للأثر المحلي تُسجل المطالبة والنتيجة مع الأثر ذريًا متى أمكن؛ للخدمات الخارجية قد لا تتاح الذرّية وتبقى النتيجة `unknown` عند التعذر. يُحدد نطاق صلاحية المفاتيح والاحتفاظ والتعافي قبل التنفيذ.
- سجل عمليات دائم محدود البيانات: وقت، `requestId`، هوية موثقة، نوع العملية، نطاق غير حساس، نتيجة، وحالة موافقة، دون نصوص أو كلمات مرور أو مفاتيح. تُحدد سياسة الاحتفاظ والصلاحيات ومعالجة فشل السجل، بما يمنع إخفاء أثر حساس أو ادعاء نجاحه عند تعذر إثباته. لا يدّعي السجل مقاومة العبث دون تصميم واختبار لذلك.

## عقد دورة الخزنة المقترح

حالة الخزنة مستقلة عن حالة المخزن `persistent`/`volatile`/`unavailable`؛ كلتاهما تُعرضان دون كشف مفاتيح أو بيانات. الحالات والعمليات أدناه **غير موجودة بعد**:

| الحالة | المعنى | العمليات المبدئية الممكنة |
|---|---|---|
| `uninitialized` | لم تُنشأ خزنة في الموقع المحدد | `initialize` بعد موافقة المستخدم |
| `locked` | خزنة موجودة ومغلقة | `unlock`، أو بدء مسار الاستعادة المصرح به |
| `unlocked` | نجح الفتح في جلسة المضيف | `lock`، تغيير عبارة المرور، تدوير DEK، تصدير مشفر بحسب السياسة |
| `recovery_required` | وضع استعادة يختاره المستخدم أو يحدده فحص موثوق وفق سياسة مُعرّفة | محاولة الاستعادة أو الإلغاء؛ ليس نتيجة تلقائية لكل كلمة مرور خاطئة |
| `unavailable` | خطأ ملف أو إصدار غير مدعوم أو تعذر تخزين/تحقق | إبلاغ آمن دون تغيير البيانات؛ لا انتقال صامت إلى ذاكرة مؤقتة |

تُمنع العمليات المتعارضة أثناء تهيئة أو تغيير كلمة مرور أو تدوير أو استعادة؛ تُعرَض حالة تشغيلية مؤقتة، وتُصمم المعاملات/التعافي أولًا. كلمة مرور خاطئة أو فشل تحقق مشترك لا يثبتان أي سبب بمفرده، ولا يُكشف تفصيل يساعد على التخمين. القفل يمنع العمليات اللاحقة لكنه لا يمحو نصًا رآه الوكيل أو يضمن مسح ذاكرة JavaScript.

| العملية المقترحة | شرط النجاح والفشل |
|---|---|
| `initialize` | موقع جديد وموافقة، توليد مفاتيح وتغليفها وتخزين ترويسة قابلة للفتح؛ فشل لا يستبدل مخزنًا موجودًا. |
| `unlock` / `lock` | فتح موثق يُبقي المفاتيح في المضيف للجلسة، أو قفل يمنع القراءات اللاحقة؛ لا تخزين كلمة المرور أو المفاتيح في السجل أو المتصفح. |
| `changePassphrase` | إعادة تغليف DEK ذريًا بمفتاح مشتق جديد؛ فشل يحافظ على طريقة الفتح السابقة. لا يعني تغيير كلمة المرور إبطال DEK المكشوف. |
| `rotateDEK` | مفتاح جديد وإعادة تشفير قابلة للتعافي، ثم اختبار القراءة قبل إيقاف القديم؛ لا يمحو بيانات أو مفاتيح سبق نسخها. |
| `recovery` | استعادة بمفتاح مستقل إن تم إعداده سابقًا؛ فقدان كل وسيلة قد يعني فقد البيانات. لا باب خلفي مضمون. |
| `encryptedExport` / `encryptedRestore` | موافقة وحدود موارد وصيغة مستقلة موثقة؛ فشل التحقق/الاستعادة لا يغير المصدر أو يمحو الأصل. |

## قرارات التشفير التي يجب اعتمادها قبل البرمجة

هذه **قيم وخيارات مراجعة** وليست مواصفات منفذة أو معتمدة أمنيًا بعد:

1. **scrypt:** اقتراح بداية للقياس: `N=65536, r=8, p=1`، وsalt عشوائي 16 بايت على الأقل ومخرج 32 بايت، بحد ذاكرة Node صريح 96 MiB. يستخدم التنفيذ API غير متزامن مع حدود للتوازي ومعدلات الطلب حتى لا يحجب حلقة الأحداث أو يستنزف موارد الجهاز. تُقبل فقط مجموعات معلمات مسموحة محددة مسبقًا قبل KDF؛ لا يُسمح لملف بتحديد استهلاك اعتباطي. تُختبر القيم على الأجهزة المستهدفة وتُراجع أمنيًا قبل اعتمادها، مع خطة واضحة إذا كانت الموارد غير كافية؛ لا تخفيض صامت.
2. **AAD وصيغة السجل:** اقتراح `version=1` مع ترميز JSON حتمي وفق RFC 8785 ثم UTF-8، وحقل نطاق ثابت يميز الاستخدام، ومعرّفات موحدة بصيغة مقيدة وإصدار عدد صحيح ضمن المدى الآمن. تُربط هوية المالك والمساحة والسجل ونوعه ومراجعته و`keyId` والخوارزمية والإصدار. يرفض المحلل الأنواع والحقول أو الإصدارات غير المعروفة قبل فك التشفير؛ اختبارات متجهات التوافق وتعديل كل حقل مطلوبة. لا يُستخدم هذا بوصفه حماية من حذف البيانات أو rollback كامل.
3. **nonce:** لا يُقبل تنفيذ حتى يثبت تصميم يمنع إعادة الاستخدام للمفتاح ذاته عبر عمليات متزامنة واستعادة أو نسخ قديمة. مرشح للمراجعة هو عداد 64-bit محجوز ذريًا لكل DEK مع prefix 32-bit وثبات الحجز قبل التشفير، ومفتاح جديد قبل الكتابة بعد استعادة معروفة؛ يخالف هذا الاختيار اقتراح الـnonce العشوائي في التصميم السابق ويحتاج قرارًا صريحًا قبل اعتماد أي منهما. لا تستطيع قاعدة قابلة للنسخ/الإرجاع وحدها إثبات عدم حصول rollback أو استنساخ خفي؛ يلزم مرجع monotonic موثوق غير قابل للإرجاع أو حد تشغيل يمنع الكتابة عندما يتعذر ضمان الشرط. عشوائية 96-bit مع حد استخدام تقلل الاحتمال ولا تضمن عدم التصادم. لا يُوصف أي مرشح بأنه ضمان قائم حاليًا.

## النسخ القديمة والترحيل دون تلف

- تبقى صيغة `mivw.notes` الإصدار 1 بصيغتها الحالية **JSON غير مشفر**، وحدها الحالي 10,000 ملاحظة و50 MiB، واستعادتها الحالية إلى مخزن فارغ. لا يُغيّر معناها أو يُعلن أنها مشفرة. النسخة المشفرة المستقبلية بصيغة ومعرّف وإصدار مختلفين؛ كشف الصيغة والتحقق منها قبل أي كتابة.
- مسار ترحيل مقترح: يختار المستخدم مصدرًا محليًا plaintext ومالكًا/مساحة بصورة صريحة بعد المصادقة، ثم ينشئ نسخة أصلية قابلة للاستعادة في مكان خاص ويقر المستخدم بحساسيتها. تُختبر الاستعادة **فعليًا** قبل اعتماد الترحيل.
- يُفحص المصدر من نسخة متسقة، بما فيها معاملات SQLite وWAL، وتُتحقق سلامة الصيغة والحدود والتعارضات قبل التغيير. لا تُنسب البيانات القديمة تلقائيًا إلى أول جلسة؛ يحدد المالك الموثق ذلك صراحةً، ولا تُمنح صلاحيات للوكلاء تلقائيًا.
- تُكتب البيانات إلى هدف جديد منفصل مع IDs وروابط ملكية محفوظة أو جدول تحويل قابل للتحقق، وتُتحقق الأعداد والمحتويات والملكية والاستعادة قبل التبديل الذري حيث تسمح المنصة. عند الفشل يبقى الأصل صالحًا؛ لا حذف أو إعادة تسمية أو استبدال للبيانات الأصلية دون موافقة مستقلة. لا وعود محو آمن لملفات أو نسخ أو WAL قديمة.
- لا يُستخدم حد التصدير الحالي بوصفه حلًا للبيانات الأكبر؛ يلزم تنسيق جديد قابل للتدرج وحدود واضحة واستعادة موثقة قبل ادعاء دعم أحجام أكبر. أي استيراد يفوق حدود الصيغة القديمة يُرفض بوضوح دون فقد.

## مصفوفة قبول قبل التنفيذ والربط

| المجال | اختبارات مطلوبة مستقبلًا |
|---|---|
| K2 | مستخدمان ووكيلان، موارد ومساحات خاصة ومشتركة، رفض الوصول المتقاطع، صلاحيات قراءة/كتابة منفصلة، منح وإلغاء وسباق الإلغاء مع الأثر. |
| المضيف | تزوير الهوية والجلسة، CSRF وOrigin/Host، عدم وصول الواجهة للمخزن أو المفاتيح، مهلة ورفض وموافقة مرة واحدة، تكرار الطلب والسباقات وحالة `unknown`. |
| NoteStore والترحيل | البيانات القديمة مع WAL، إسناد ملكية صريح، تعارضات، فشل في كل خطوة واستعادة الأصل، عدم فقد أو كتابة جزئية، إعادة فتح عملية مستقلة. |
| الخزنة | دورة الحالات، كلمة مرور خاطئة وتلف، تعديل AAD/tag/ciphertext، تدوير وإعادة تغليف وتعطل، تزامن nonce واستعادة وrollback، حدود KDF والموارد. |
| النسخ | تمييز plaintext القديم، تصدير مشفر بحجم كبير، اقتطاع أو تغيير المقاطع، استعادة بعد الإغلاق وعلى جهاز آخر، عدم استبدال أصل عند الفشل. |
| الإصدار | فحص محلي وCI مستقل قابل للمراجعة بعد إعداده، وتوثيق كل اختبار متعذر؛ لا دمج أو نشر أو ربط واجهة حتى اجتياز البوابات المعتمدة. |

الترتيب المقترح: عقود K2 والهوية أولًا، ثم المضيف وNoteStore والترحيل في وحدات قابلة للاختبار، ثم مراجعة واعتماد تفاصيل الخزنة قبل التشفير، ثم النسخ المشفرة، وأخيرًا الواجهة. لا يُستخدم نجاح اختبارات K1 المحلية كإثبات لاستيفاء أي بوابة لاحقة.
